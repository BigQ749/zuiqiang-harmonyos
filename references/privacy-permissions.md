# 隐私、权限与协议的实际状态

## 既有政策优先

用户要求编辑原有托管政策时，先定位当前产品/语言/政策 ID，修改原记录，不另建同名新政策。**编辑保存、生成协议、提交协议审核、审核通过、版本关联、客户端生效是不同阶段**；分别记录状态。不能只保存编辑就说公开政策已更新，也不能为“完成”擅自生成或提交审核。

用户协议是否必填以当前后台字段、产品业务和平台规则为依据，不统一宣称所有应用都必须新建一份。已有有效协议能用则复用；隐私政策独立准确。托管与自有 URL 按产品选择：不能一概禁止 GitHub Pages，也不能保证其中国大陆可达；自有 URL 必须可匿名访问、稳定且内容对应当前产品，托管方案验证实际关联和生效。

首启托管提示只在确认目标平台配置与客户端支持时由系统承接；不机械删除现有隐私交互导致没有同意入口，也不保留两套重复弹窗。系统通知引导是功能授权，不与政策同意混成一项。通知引导应有关闭/稍后，允许后及时重查状态并关闭引导，拒绝后设置页可再次进入。

## 从最终包建立权限—数据对照

以最终签名 HAP 的 requestPermissions 为事实起点，逐项记录：权限/API、是否 user_grant、触发页面和时机、实际读到的数据、用途、处理地点、留存、拒绝后影响、AGC 政策权限清单和标签。

- 包里 CAMERA、LOCATION、APPROXIMATELY_LOCATION 等 user_grant 权限与托管权限容器逐项一致；只在正文提到定位不能替代结构化权限项。改 manifest 后重签、重验、更新后台，不加包里不存在的权限来讨好校验。
- 系统 CameraPicker 与直接 Camera Kit/WebRTC 不同：按对应 SDK 的官方说明决定是否需要本 App CAMERA；不能为了首启一定出现权限框随意加权限。直接访问相机/麦克风要检查声明、系统授权、ArkWeb 请求回调和真实使用四层。
- 系统 PhotoPicker/保存对话框授权所选项目，不等于获得全图库读取权限。确实使用精确/模糊位置就写真实用途，不因为“单机”隐藏定位；没有定位则不勾。
- 本机处理不等于没有处理个人信息，也不自动等于“收集/关联/跟踪”所有字段都选是。按平台当时对各字段的定义，逐项核对实际行为；照片、录音、经期、课程、位置等不能全部硬塞“其他信息”。没有广告、账号、统计 SDK 就不编这些业务场景。

## 模板内容

功能条款写真实路径、必要信息、用途及不提供的影响；不存在基本/全量双模式就不编设置入口。保留期限区分内存、缓存、私有记录、用户导出相册；导出文件由用户删除，不因卸载必然消失。无服务器写无服务器本机处理，不虚填“中国境内服务器”。真实开发者联系方式必须来自已确认信息，不猜。

所有文案和标签要与实际包、SDK、日志/上传行为一致；不得承诺“永不联网”却包含远程资源或分析上传。位置、健康等业务资质按实际功能和审核要求核实，不为改分类而虚构资质或医疗承诺。

## 原政策更新产生新修订时

对已有托管政策执行“更新”可能在同一政策记录下生成新的修订版本。分别保存政策记录ID与修订ID，核对列表仍是一条原记录；不能仅因出现新版本ID判定另建了政策。为线上旧版本保留旧完成修订，勿删除其正在使用的协议。

新修订提交审核成功不代表已完成、可选或已关联。涉及本次权限删除时，等待匹配新包的修订完成且在版本页可选择后，再关联、保存并继续提审；不可为赶进度关联仍含旧权限的已完成政策，或把旧同名项当最新修订。报告外部审核等待与实际阻塞点，不伪报生效。
